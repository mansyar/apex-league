A push to `main` now verifies, builds and uploads `apps/client/dist` to a
Cloudflare Pages project. The upload cannot run unless `bun run verify` and
`bun run build` both succeed, and a failed upload leaves the previous deployment
serving.

`bun run deploy` is the same command the workflow runs, so a local deploy and a
CI deploy cannot drift. The script carries neither the directory nor the project
name: `wrangler.jsonc` supplies both.

### `.github/workflows/deploy.yml` (full source, as committed)

```yaml
# Deploy the client to Cloudflare Pages when main moves.
#
# The gate that protects pull requests protects production: this job re-runs
# `bun run verify` (type checks, typed tests, Biome, the voxel determinism gate)
# and only then builds and uploads `apps/client/dist`. A failing check fails the
# run before the upload step, so nothing is published and the previous
# deployment stays live.
#
# One-time setup (README, "Deploying"): a Cloudflare Pages project named in
# `wrangler.jsonc`, plus two repository secrets — `CLOUDFLARE_API_TOKEN` with
# the Pages: Edit permission and `CLOUDFLARE_ACCOUNT_ID`.
name: Deploy

on:
  push:
    branches: [main]
  # Manual re-run. Anything other than main lands as a Pages preview
  # deployment, not on the production URL.
  workflow_dispatch:

permissions:
  contents: read

# One deploy per branch. A newer push to main cancels the run in flight, so
# production never lands on a stale build.
concurrency:
  group: deploy-${{ github.ref }}
  cancel-in-progress: true

jobs:
  deploy:
    name: Deploy (verify, build, upload)
    # The canonical repository only: a fork's push carries no secrets and must
    # not attempt an upload.
    if: github.repository == 'mansyar/apex-league' && github.event.repository.fork == false
    runs-on: ubuntu-latest
    steps:
      - name: Check out
        uses: actions/checkout@v4

      - name: Set up Bun
        uses: oven-sh/setup-bun@v2
        with:
          # Kept in lockstep with ci.yml and nightly.yml.
          bun-version: 1.4.2

      - name: Cache Bun install cache
        uses: actions/cache@v4
        with:
          path: ~/.bun/install/cache
          key: ${{ runner.os }}-bun-${{ hashFiles('bun.lock') }}
          restore-keys: |
            ${{ runner.os }}-bun-

      - name: Install dependencies
        run: bun install --frozen-lockfile

      # Fail in seconds rather than after the gate if the credentials are not
      # configured. Only secret *names* are printed; the values never leave
      # `env:`, so nothing is echoed even under `set -x`.
      - name: Check deploy secrets
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          CLOUDFLARE_ACCOUNT_ID: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
        run: |
          missing=""
          if [ -z "${CLOUDFLARE_API_TOKEN}" ]; then
            missing="${missing} CLOUDFLARE_API_TOKEN"
          fi
          if [ -z "${CLOUDFLARE_ACCOUNT_ID}" ]; then
            missing="${missing} CLOUDFLARE_ACCOUNT_ID"
          fi
          if [ -n "${missing}" ]; then
            echo "::error::Missing repository secret(s):${missing}."
            echo "::error::Add them under Settings > Secrets and variables > Actions."
            exit 1
          fi
          echo "Both deploy secrets are present."

      - name: Verify (types, tests, biome, voxel determinism)
        run: bun run verify

      - name: Build
        run: bun run build

      # wrangler will not create a Pages project non-interactively, so without
      # this a first deploy would need a manual `pages project create`. The step
      # is a no-op once the project exists, and the name comes from
      # `wrangler.jsonc`, the only place it is written down.
      - name: Ensure the Pages project exists
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          CLOUDFLARE_ACCOUNT_ID: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
        run: |
          project="$(sed -n 's/^[[:space:]]*"name"[[:space:]]*:[[:space:]]*"\([^"]*\)".*/\1/p' wrangler.jsonc)"
          if [ -z "${project}" ]; then
            echo "::error::No top-level \"name\" in wrangler.jsonc."
            exit 1
          fi
          echo "Pages project: ${project}"
          projects="$(bunx wrangler pages project list --json)"
          if printf '%s\n' "${projects}" | grep -qF "\"${project}\""; then
            echo "The project already exists."
          else
            echo "Creating the project (first deploy only)."
            bunx wrangler pages project create "${project}" --production-branch main
          fi

      # Runs only when every earlier step succeeded. `success()` is the default
      # step condition; it is spelled out so the gate is visible in the source.
      - name: Deploy to Cloudflare Pages
        if: success()
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          CLOUDFLARE_ACCOUNT_ID: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
        # `--branch` is passed explicitly: if checkout ever leaves a detached
        # HEAD, wrangler would read the branch as "HEAD" and publish a preview
        # deployment instead of production.
        run: bun run deploy -- --branch "${{ github.ref_name }}"
```

### `wrangler.jsonc`

```jsonc
{
  // Cloudflare Pages project. The deployed site is https://<name>.pages.dev/.
  // Renaming the project is a one-line change here; the deploy workflow reads
  // this name rather than repeating it.
  "name": "apex-league",
  // Vite writes the production bundle here (`bun run build`).
  "pages_build_output_dir": "apps/client/dist"
}
```

Wrangler's Pages validator (`validatePagesConfig`, `wrangler-dist/cli.js:32300`)
requires exactly this shape: a top-level `name` and `pages_build_output_dir`,
and it rejects `main` alongside the latter. Both keys are accepted by
`biome check`, so the file does not disturb the gate it sits behind.

## Notes

- **No committed test covers workflow or config contracts, so the assertions
  live in the evidence harness.** A search of every `*.test.ts` found no suite
  that reads `.github/**`, `package.json` or a workflow file, and this phase's
  `Touches` contains no test file. Rather than invent a home for them, the ten
  harness files stay under `.conductor/evidence/` (gitignored, not discovered by
  `bun test`, not type-checked by `bun run check` since they sit outside every
  `tsconfig` `include`). They are runnable as written:

  ```

  bun test ./.conductor/evidence/phase-2-yaml-shape.test.ts
  bun test ./.conductor/evidence/phase-2-gate-order.test.ts
  bun test ./.conductor/evidence/phase-2-workflow-shell.test.ts
  bun test ./.conductor/evidence/phase-2-deploy-nocreds.test.ts
  bun test ./.conductor/evidence/phase-2-deploy-args.test.ts
  bun test ./.conductor/evidence/phase-2-probe-node.test.ts
  bun test ./.conductor/evidence/phase-2-probe-invocation.test.ts
  bun test ./.conductor/evidence/phase-2-probe-bun.test.ts
  bun test ./.conductor/evidence/phase-2-bundle.test.ts
  ```

  Each prints the values it asserts. **Gap for a later track:** if these
  contracts deserve permanent protection, they need a committed suite in a
  `Touches` set that allows it.
- **`bunx` in the deploy script, not a bare `wrangler`.** `node_modules/.bin/wrangler`
  starts with `#!/usr/bin/env node` and `bin/wrangler.js` refuses to run below
  Node 22 (`MIN_NODE_VERSION`). `bunx wrangler` makes Bun execute the entry
  point instead. `phase-2-probe-node` proves the difference: on a PATH holding
  only Bun, `node` is not found, yet `bunx wrangler --version` prints
  `4.152.0` and `bun run deploy -- --help` exits 0. The pinned `setup-bun@v2`
  runner image happens to ship a modern Node, but the deploy should not depend
  on that.
- **Why the workflow creates the Pages project itself.** The spec's first-deploy
  edge case assumes `wrangler pages deploy` creates a missing project. It does
  not, not in this version: with a `name` configured, no existing project and
  no TTY, wrangler throws `UserError: The Pages project "<name>" does not exist
  … start by running: wrangler pages project create`
  (`wrangler-dist/cli.js:308651`). The interactive path that does create a
  project is unreachable on a runner. The `Ensure the Pages project exists` step
  closes that gap: it reads the name out of `wrangler.jsonc` (the one place it
  is written), lists the account's projects, and creates the project only when
  it is missing — so a first deploy works and an existing project is a no-op.
  `phase-2-workflow-shell` exercises all three branches (exists, missing,
  listing fails).
- **The secret check runs before the gate on purpose.** A missing secret fails
  in seconds with the secret's name and where to add it, instead of after a
  four-minute verify. It prints names only; values stay in `env:`.
- **Fork gate.** The job is conditioned on
  `github.repository == 'mansyar/apex-league' && github.event.repository.fork == false`.
  A fork's push skips the job entirely rather than failing it, and a fork has no
  access to the secrets in the first place.
- **Concurrency.** `group: deploy-${{ github.ref }}` with
  `cancel-in-progress: true` means a newer push to `main` cancels the run in
  flight, so production cannot land on a stale build. The group is scoped to the
  ref, so a `workflow_dispatch` from another branch cannot cancel a `main`
  deploy.
- **`--branch` is explicit.** Without it wrangler reads the branch with
  `git rev-parse --abbrev-ref HEAD`; a detached HEAD would yield `HEAD` and
  publish a preview deployment instead of production. Passing
  `"${{ github.ref_name }}"` removes the failure mode.
- **AC-8 is configuration-and-reasoning, not a live drill.** No Cloudflare
  account or token exists yet, so a real failed upload could not be staged.
  What is proven is the part that lives in this repository: nothing in the job
  unpublishes the site, nothing swallows the failure, and a failed upload exits
  non-zero. The remaining link — Pages keeping the previous deployment live
  until a new upload succeeds — is Cloudflare's documented behaviour and is
  recorded here as an assumption to confirm on the first real deploy.
- **Live deploys are blocked on owner setup, by design.** This phase is complete
  and verifiable in-repo without credentials; only the live half of AC-1 and the
  live half of AC-8 need them.
- `bun run verify` reports one pre-existing Biome warning
  (`noDescendingSpecificity` in `apps/client/src/ranch.css`). Warnings do not
  fail the gate, and the file is untouched by this phase.
- Nothing under `packages/` changed, the client runtime is untouched, and
  `SAVE_VERSION` is still 25 — this phase adds CI configuration and a dev
  dependency only.
- **Re-verification at the phase head.** After this file was committed
  (`f8f2bc69`), the phase command was re-run against that head with a clean
  tree: `bun test --check --parallel=4 --timeout 120000` → 2807 pass, 1 skip,
  0 fail, 267347 expect() calls, 2808 tests across 240 files, 44.73 s. The count
  is identical to the pre-commit run, which also confirms the ten evidence
  harnesses are still invisible to a bare `bun test`.

### Owner steps for the first live deploy

1. Create a Cloudflare account with Pages enabled (or use an existing one).
2. Create an API token: Cloudflare dashboard → My Profile → API Tokens →
   Create Token → "Cloudflare Pages — Edit" (account-scoped), and copy it.
3. Copy the account id from the dashboard's overview page (right-hand column).
4. In GitHub: repository → Settings → Secrets and variables → Actions → New
   repository secret, twice:
   - `CLOUDFLARE_API_TOKEN` = the token from step 2
   - `CLOUDFLARE_ACCOUNT_ID` = the id from step 3
5. Push to `main`. The run creates the `apex-league` Pages project if it does
   not exist, then uploads `apps/client/dist`. The site appears at
   `https://apex-league.pages.dev/`.
6. To use a different project name, edit `"name"` in `wrangler.jsonc` — the
   workflow reads it from there, and nothing else needs to change. The URL
   follows the name.
