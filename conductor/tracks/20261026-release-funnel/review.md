## Summary

The Release Funnel delivers what it set out to: a deploy path that is gated on
the same verification that protects pull requests, a smoke check that proves
the deployed artifact works and is proven able to fail, a config free of
machine-specific state, and documentation that describes the deployment
accurately without claiming a live site that does not exist.

The reviewer found **0 Critical, 0 High, 4 Medium, 4 Low**. Under
`review.strict: true` nothing is deferred: all eight findings go to a Phase R1
and must be fixed before the PR opens.

The most substantive findings are not cosmetic:

- **F1** — the smoke check's request-log parser returns `[]` silently and
  `violations()` has no "no requests observed" rule, so the deploy-time smoke
  step can print `requests 0 · failed 0` and exit 0. The console parser in the
  same file fails loud in the identical situation; the request parser has no
  counterpart. That is a vacuous pass of the very check AC-3 depends on.
- **F2** — the deploy job provisions Bun but never Node, while the pinned
  `wrangler` bin wrapper hard-refuses anything below Node 22
  (`node_modules/wrangler/bin/wrangler.js:5,12-22`) behind a

  `ubuntu-24.04` image. If `bunx` honours the shebang there, **every** wrangler
  call fails before reaching the API and the deploy never uploads — a failure
  that would surface only on the owner's first live push.
- **F3** — `conductor/workflow.md:381-391` still asserts "There is no
  automated deployment: no hosting workflow exists, and the track workflow
  never deploys". This diff *is* that workflow. The section's own instruction
  to "add the commands to this file at that point" was not honoured.
- **F4** — the phase-2 workflow contract assertions live only under the
  gitignored `.conductor/evidence/`, so nothing committed fails if a later
  edit moves `Deploy` above `Verify` or inlines a secret. The gate is the
  product of this track.

Two things this review explicitly did **not** treat as findings:

- The three credential-pending acceptance criteria (AC-1, AC-3's live half,
  AC-8's live half). The spec anticipated the missing secrets; the primary
  recorded them as *partial*, with the DNS evidence and the reason — not as

- `scripts/` sitting outside every workspace `tsconfig` `include`. The

## Findings

### F1 — Medium — `scripts/smoke/smoke.ts:132-142, 154-181`

**What.** `parseRequests` returns `[]` when the CLI's request listing does not
match the expected `N. [GET] url => [status]` shape, and `violations()` never
treats "no requests observed" as a violation. The deploy-time smoke step would
print `requests 0 · failed 0` and exit 0 — a vacuous pass of the request-log
half of AC-3. The console parser at `:117-119` deliberately fails loud in the
identical situation, and that asymmetry is asserted by a committed test
(`smoke.test.ts:170-172`); the request parser has no counterpart.

**Why.** The request log is the only evidence for "zero failed network
requests for JS/CSS/GLB/font assets". A CLI output-format change silently
degrades the release gate to a green run that verified nothing about assets.

**Fix.** In `violations()`, push a violation when `requests.length === 0`, or
make `parseRequests` `fail()` when the body contains no `=> [status]` line,
mirroring `parseConsoleReport`.

**Requirement.** AC-3, FR-3

**Test gap.** Committed test: "an empty request log is a violation, not a
silent pass" in `scripts/smoke/smoke.test.ts`.

### F2 — Medium — `.github/workflows/deploy.yml:41-56, 101-119`

**What.** The job provisions Bun but never Node, while the pinned `wrangler`'s
bin wrapper hard-refuses Node < 22 (`node_modules/wrangler/bin/wrangler.js:5,12-22`:
*"Wrangler requires at least Node.js v22.0.0"*) and the bin's shebang is
`#!/usr/bin/env node`. `bunx wrangler --version` resolves the local isolated
install and runs it, but the local machine happens to have Node v24.16.0 on
PATH, so the local success says nothing about the runner, whose default `node`
is 20.x on the `ubuntu-24.04` image.

**Why.** FR-1/AC-1 depend on `wrangler pages deploy` actually running in CI.
The workflow's success currently rests on an undeclared, unpinned property of
the runner image, and the failure appears only on the first live push.

**Fix.** Add one step to the deploy job, before any wrangler call:
`actions/setup-node@v4` with `node-version: 22`. That satisfies wrangler's own
`MIN_NODE_VERSION` under either runtime choice and removes the dependency on
the runner image's default Node. The `bunx --bun` alternative is **withdrawn**:
it mis-parses in Bun 1.4.3-canary.1 and reaches for the network. Optional
hardening, not required to close this finding: echo `bunx wrangler --version`
in an install step so a bad runtime fails in seconds rather than at the upload
step.

**Requirement.** FR-1, AC-1

**Test gap.** None practical; a version echo would fail loudly and early.

### F3 — Medium — `conductor/workflow.md:381-391`

**What.** The "Release & Deployment" section still says "There is no automated
deployment: no hosting workflow exists, and the track workflow never deploys"
and defers static hosting until release work begins — but this diff adds
exactly that workflow. The section's own instruction to "add the commands to
this file at that point" was not honoured.

**Why.** `workflow.md` is what the next track reads before planning; the
stale sentence will produce a wrong plan (a manual upload assumed, or hosting
re-added). The false statement is produced by this diff, so it should be
corrected on this branch rather than after the merge.

**Fix.** Rewrite `workflow.md:381-391` to describe the deploy workflow: the
push-to-`main` trigger plus `workflow_dispatch`, the `bun run verify` gate,
`wrangler.jsonc` as the single source of the project name and upload dir, the
two owner-created secrets, the post-upload smoke check, and the still-true
"no deployment has run yet".

**Requirement.** FR-7, AC-7

**Test gap.** n/a (prose).

### F4 — Medium — `.github/workflows/deploy.yml:1-137`, `package.json:11`, `wrangler.jsonc:1-8`

**What.** The phase-2 contract assertions (deploy gated behind
`bun run verify`; secrets never echoed in a `run:` body; fork gate; upload dir
= `apps/client/dist`; `--frozen-lockfile`; project name read from one file) live
only in `.conductor/evidence/phase-2-*.test.ts`, which is gitignored and
therefore not discovered by `bun test`. Nothing committed fails if a later edit
moves `Deploy` above `Verify`, inlines a secret, drops `--frozen-lockfile`, or
renames the upload directory.

**Why.** The gate *is* the product of this track ("a red gate never reaches the
site"). A silent future edit could let a red build ship behind a green CI
badge, and the failure mode is invisible until a real release.

**Fix.** Commit a small source-shape test asserting step order, the deploy
step's `if: success()`, no `${{ secrets.* }}` inside any `run:` body,
`bun install --frozen-lockfile` present, `pages_build_output_dir` =
`apps/client/dist`, and the fork gate. The repo already has this pattern
twice (`apps/client/vite.config.test.ts`, `scripts/smoke/smoke.test.ts`), and
`bun test` discovers root-level `*.test.ts` files automatically.

**Requirement.** FR-1, FR-2, NFR-3, AC-2

**Test gap.** The committed source-shape test is itself the gap.

### F5 — Low — `scripts/smoke/smoke.ts:196-199`

**What.** A bare `--url` with no value leaves `argv[at + 1]` undefined, so
`fromFlag` is undefined and the function silently falls through to `SMOKE_URL`
or the default Pages URL instead of reporting the malformed invocation.

**Why.** In CI the default target is production; a mistyped flag would smoke
production while the operator believed they pointed at a local build.

**Fix.** If `at !== -1 && fromFlag === undefined`, `fail("--url needs a
value")`.

### F6 — Low — `scripts/smoke/smoke.ts:314-321, 332-341`

**What.** (a) In the catch path, `violations(gather())` can itself throw
(unreadable probe, console header missing), and that error replaces the
original reason — e.g. "the ranch to boot did not happen within 60s" is lost
exactly in the broken-build case the catch exists to diagnose. (b)
`readFileSync`, `targetUrl` and `resolveCli` run *before* the try/catch, so a
missing `wrangler.jsonc` or an absent `playwright-cli` escapes as an uncaught
stack trace rather than the documented `RESULT fail` + JSON envelope.

**Why.** The smoke step's output is the release evidence; a stack trace instead
of a structured failure is harder to read in the Actions log, and the lost
reason is the diagnosis.

**Fix.** Guard the catch body's `gather()` with its own try/catch that falls
back to the original message; move the three pre-try computations inside the
try (or convert their errors to the same JSON envelope).

**Requirement.** FR-5, AC-5

**Test gap.** —
