## Behaviour-identity review

- **Rendered DOM**: `hud/shell.ts` appends `scoreBug.root, motionWrap,
  lineage.root, hudStack, resetModal, creatureDetail.root, handbook.root,
  settings.root` — the base order — and `createHud` appends `hints.root` (the
  callout) last, exactly where it sat in the base `root.append`. Builder
  bodies, class names, `aria-*` attributes, `style.display` defaults and
  `hud-stack` assembly are verbatim.
- **Copy**: every string literal moved with its function; no line was reworded,
  re-punctuated or added. `copy.test.ts` (pinned copy) passes unchanged.
- **Update path**: `store.subscribe` → `hud.update` → the same single paint, in
  the same statement order. The one-update bookkeeping that used to be local to
  `createHud` (`prevAp`/`apPips`, `prevLadder`/`climbLine`, `lastFocus`) now
  lives in the `createHudUpdate` closure — same lifetime, same reset points.
- **Hint lifecycle**: `shownHintId`, the dismissal handler (persist then clear)
  and the first-unseen-hint block moved into `createHints`; `update` calls
  `hints.sync(state)` at the exact point the block occupied. `seenHints`
  persistence is unchanged.
- **Interaction state**: `pickerOpen`, `creatureOpen`, `dockOpen`, `renaming`
  and `current` moved onto `HudViewState`; every read/write site was renamed
  mechanically. The shell's own toggles re-render through the injected
  `shell.render`, which `createHud` assigns to `update` before returning — the
  same self-call the base made on `update(current)`.
- **Construction order**: the base built score bug → creature plate → dock →
  reset modal → settings modal → handbook → pref cluster → detail modal →
  lineage plate → callout. The shell keeps that order and the callout is built
  by `createHints` immediately after, before `root.append`, so
  `window.matchMedia` is consulted at the same point in boot as before.

## Deviations

1. **`hud/types.ts` is a new fifth module** (the brief prescribed
   `shell` / `update` / `hints` + `hud.ts`). Invariant 4 requires the three
   passes not to import each other, and all three need the same refs/view types;
   the brief's own escape hatch ("shared types go into a small module, as
   `app/screen-deps.ts` did") is what this uses. 2,237 B.
2. **`hud/copy-cup.ts` carries the whole `HINTS` table**, including the two
   care/kit hints (`ap-basics`, `training-tier`) and the two legacy hints
   (`graduation-ready`, `prestige-*`). `selectHint` is `Array.find` over one
   array — the order *is* the teaching order and the precedence rule, so the
   table cannot be split across the domain modules without changing which hint
   wins. The module therefore owns the cup/ladder/gatekeeper copy plus the
   ordered onboarding table, which is the brief's "cup, ladder … copy" seam.
3. **The plan's copy split listed a `hints` module; the brief's listed
   `copy-cup`.** The brief was followed: hint *selection* (`selectHint`) lives
   in `hud/copy-cup.ts` and hint *lifecycle* (callout, dismissal, `onHintSeen`)
   in `hud/hints.ts`. `copy.ts` re-exports `selectHint` and `HudHint`, so the
   public copy surface is unchanged.
4. **`saveFailureNotice`, `corruptSaveNotice` and `spendFlashIndex` went to
   `copy-care.ts`.** The prescribed seams name no home for the routine/system
   lines; they are neither growth/graduation nor cup/ladder copy, and
   `statusLine` (care) composes the care family.
5. **`hud.ts` is a composition root, not a pure facade.** It keeps
   `HudHandlers`, `Hud`, `createHud` and the pre-existing re-export blocks,
   which is what the brief prescribes; only `plates.ts` and `copy.ts` are
   re-export-only facades.
6. **`hud/shell.ts` takes a structural handler type** (`HudShellHandlers`, the
   subset it wires minus `onHintSeen`) instead of importing `HudHandlers` from
   `../hud`, which would create the very cycle invariant 4 forbids. A
   `HudHandlers` satisfies it, so `createHud` passes `handlers` unchanged.
